1. Structure Basics

There are 5 main structures in html

  1. Plain text contents (Text nodes)
  2. Comments
  3. The Doctype Declaration
  4. Character Entities
  5. The Elements

1. Plain Text Content (Text Nodes)

The simplest piece of HTML isn't a tag at all — it's just the words themselves. Any text sitting between tags is called a text node, and it's what the reader actually sees rendered on the page. 

<p>This part right here is the text node.</p>

Tags give structure and meaning, but the text node is the actual content — strip away every tag on a page, and the text nodes are what's left.

2. Comments

Comments let you leave notes in your code that the browser completely ignores — nothing inside a comment ever renders on the page. They're written like this: 

<!-- This is a comment, the browser skips it -->

Useful for leaving reminders for yourself, explaining why a piece of code exists, or temporarily "switching off" a chunk of HTML without deleting it while testing.

3. The DOCTYPE Declaration

Every HTML document should start with a single line before the <html> tag: 

<!DOCTYPE html>

This tells the browser "read this page using modern HTML5 rules." Without it, older browsers can fall back into something called quirks mode — an old compatibility mode that renders CSS and layout inconsistently, mimicking bugs from browsers in the late 90s. It's not a tag, has no closing tag, and always goes exactly once at the very top of the file.

4. Character Entities

Some characters can't be typed directly into HTML because the browser would confuse them with actual code — most importantly < and >, since those are how tags are written. To display them as plain text, you use a character entity instead: a short code starting with & and ending with ;.

You want to showYou write
<&lt;
>&gt;
&&amp;
a non-breaking space&nbsp;
©&copy;

You've actually already seen one in the example from earlier — Welcome to my blog &amp; portfolio! uses &amp; so the ampersand displays correctly instead of potentially being misread as the start of another entity.

5. The Elements

An element is the full package: an opening tag, its attributes, the content inside, and the closing tag. This is the "bigger picture" piece — everything else on this list (text nodes, comments, entities) exists inside or around elements. 

<p class="intro">Welcome to my blog &amp; portfolio!</p>
  • Tag: p — defines what kind of element it is
  • Attribute: class="intro" — extra info about the element
  • Text content: "Welcome to my blog" — the text node inside it
  • Character entity: &amp; — the escaped ampersand

Put together, that single line uses all five structures from this section at once — which is a nice way to end this part: none of these pieces exist in isolation, they combine to make up everything you'll ever write in HTML.

2. How Browsers Read HTML

Now that you know the raw ingredients HTML is built from, the next question is what actually happens to them the moment a browser opens your file.

What Is a Browser?

A browser (Chrome, Firefox, Safari, Edge) is a program that takes a URL, fetches the files behind it — HTML, CSS, JavaScript, images — and turns that raw text into the visual page you see and interact with. It's handling several jobs at once: networking, parsing, rendering, and running JavaScript.

What Is a Parser?

A parser is the part of the browser that reads raw text and converts it into a structured format the program can actually work with. Your HTML file is just a string of characters on disk — the parser reads it character by character, recognizes patterns like <p class="intro">, and builds an actual tree of connected objects out of it, with real parent-child relationships the browser can query and manipulate.

The Pipeline: From Text to Pixels

Once parsing starts, the browser moves through a fairly fixed sequence, often called the critical rendering path:

  1. HTML Parsing — the browser reads your HTML top to bottom, building the DOM (Document Object Model) — the tree of every element on your page.
  2. CSS Parsing — stylesheets get parsed into the CSSOM (CSS Object Model), a similar tree, but for styles instead of structure.
  3. Render Tree — the DOM and CSSOM get combined into what actually needs to be drawn. Anything set to display: none gets excluded here.
  4. Layout (Reflow) — the browser calculates the exact size and position of every box on the page.
  5. Paint — pixels finally get drawn to the screen.

The Blocking Problem

There's one snag in this pipeline worth knowing: if the parser reaches a <script> tag with no special instructions, it stops building the DOM entirely until that script finishes downloading and running. On a slow connection, that pause is very noticeable — a blank page staring back at the reader.

This is exactly why the defer and async attributes exist on <script> tags — they let the script download in the background instead of freezing the parser: 

<script src="main.js" defer></script>

defer waits until the HTML is fully parsed before running the script, in order. async runs the script the instant it's ready, with no order guarantee — better suited to independent scripts like analytics tags than to your main page logic.

Note: this whole pipeline usually takes milliseconds, but slow scripts or huge images can stretch it into seconds a reader actually notices. And don't confuse the async attribute above with JavaScript's async/await keywords — same word, but one controls script loading in HTML, the other handles waiting for data inside your JS code.

3. Document Metadata

Everything inside <head> is invisible on the page itself — none of it renders as content a reader sees. Instead, it's information about the page: for the browser, for search engines, and for anything sharing a link to it.

Character Encoding

<meta charset="UTF-8">

This tells the browser which set of characters to expect when decoding your file's text. UTF-8 covers virtually every character and symbol in use today, which is why it's the standard default — without it, special characters (accents, emoji, non-English scripts) can render as garbled text.

The Viewport

<meta name="viewport" content="width=device-width, initial-scale=1.0">

Without this line, mobile browsers default to rendering your page as if it were on a desktop screen, then shrinking the whole thing down — tiny, zoomed-out text included. This tag tells the browser to match the page's width to the actual device's width, which is the starting point for any responsive layout.

The Title

<title>My Blog</title>

The text that shows up in the browser tab, in bookmarks, and — as covered back in Section 5 — as the clickable blue headline in search results. Every page should have a unique, descriptive one.

Meta Description

<meta name="description" content="Notes on HTML, from the basics to the parts most tutorials skip.">

A short summary of the page, not visible on the page itself, but often pulled by search engines as the gray preview snippet under your title in results. Usually kept under about 160 characters.

Linking a Stylesheet

<link rel="stylesheet" href="css/style.css">

<link> connects an external file to the page — almost always used for CSS. It goes in <head> so styles are ready before the page paints, avoiding a flash of unstyled content.

Favicon

<link rel="icon" href="images/favicon.ico">

The small icon shown in the browser tab and bookmarks. Small detail, but its absence is one of the more obvious signs of an unfinished site.

Going further: there's also a family of tags called Open Graph tags (og:title, og:image, etc.) that control how a link looks when shared on social media or messaging apps. Not essential to get started, but worth a search once the rest of this feels comfortable.

4. Semantic Layout Tags

Every page needs some kind of layout — a top area, navigation, the main content, maybe a sidebar, and a bottom area. For years, developers built all of this with <div>, distinguishing each piece only by a class name: 

<div class="top-nav">...</div>
<div class="content">...</div>
<div class="side-info">...</div>
<div class="bottom">...</div>

HTML5 introduced a set of tags that describe these same regions by name, instead of relying on a class attribute to explain what something is:

  • <header> — introductory content, usually at the top of a page or section
  • <nav> — a block of navigation links
  • <main> — the primary content of the page; should appear once per page
  • <article> — a self-contained piece of content, like a blog post or news story
  • <section> — a themed grouping of content, usually with its own heading
  • <aside> — content tangentially related to the main content, like a sidebar
  • <footer> — closing content for a page or section

Rewritten with semantic tags, the layout above becomes:

<header>...</header>
<nav>...</nav>
<main>...</main>
<aside>...</aside>
<footer>...</footer>

Here's the catch: a browser renders both versions identically. No styling difference, no layout difference, nothing visible changes by switching <div class="top-nav"> to <nav>.

So does it actually matter which one you use? The answer isn't in how the page looks — it's in who else is reading your HTML besides the person looking at the screen.

5. Who Else Reads Your HTML

A human isn't the only thing that opens your page. Several kinds of automated readers process your HTML too — and none of them can "see" a layout the way a person can. What they get is your raw markup, which is exactly why the tags from Section 4 matter.

Bots

A bot is simply a program that performs actions automatically, without a human clicking through each step. That's the whole definition — what a bot actually does depends entirely on what it was built for. Some bots are welcome guests (a search engine's crawler), others are the spam accounts you've probably seen in YouTube comment sections. Same basic mechanism, very different intent.

Well-behaved bots also tend to respect a file called robots.txt, placed at the root of a site, which tells them which pages they're allowed to visit. Spam bots typically ignore it entirely.

Search Engines

A search engine has three jobs: crawl the web to discover pages, index what it finds, and rank results when someone searches. The crawling part is handled by bots — they follow every href link they encounter, which is exactly why that attribute matters beyond just letting people click things.

Once a page is crawled, its structure gets parsed and stored. This is where semantic tags earn their keep:

  • <title> becomes the clickable headline in search results
  • <meta name="description"> often becomes the preview snippet beneath it
  • <main> and <article> help the engine identify actual content, separate from navigation or boilerplate
  • <h1>–<h6> headings signal what topics matter most

A page built entirely out of unlabeled <div>s gives a crawler far less to work with than the same page built with <nav>, <main>, and <article> in the right places.

Screen Readers

A screen reader is software that reads a page aloud, or converts it to braille, for users who can't see the screen. Like a search engine's crawler, it doesn't perceive layout visually — it relies on the structure of your HTML to describe the page.

With semantic tags in place, a screen reader user can jump straight to <nav> to find navigation, or to <main> to skip straight to the actual content, instead of listening through every element on the page in order to find what they're looking for. A wall of identical <div>s gives them no such shortcuts.

This is only a first look — Section 8 goes further into concrete accessibility practices built on top of this same idea.

6. Forms

Forms are how a page collects input from a visitor — a search box, a login screen, a contact page. Everything related to a single form sits inside a <form> tag: 

<form action="/submit" method="POST">
  ...
</form>

action is where the form's data gets sent, and method is how — GET appends data to the URL, POST sends it in the request body, typically used for anything that changes data on the server (like a login or signup).

Labels and Inputs

Every input should be paired with a <label>. The for attribute on the label should match the id on the input it belongs to: 

<label for="email">Email</label>
<input type="email" id="email" name="email">

This pairing does two things: clicking the label text focuses the input automatically, and screen readers announce the label when the input is focused — without it, a screen reader user just hears "text field," with no idea what it's asking for.

Common Input Types

  • type="text" — plain text
  • type="email" — expects an email format, and mobile keyboards show the @ key
  • type="password" — masks what's typed
  • type="number" — restricts to numeric input
  • type="checkbox" — toggle, multiple can be selected
  • type="radio" — pick one from a group

Other Form Elements

<label for="topic">Topic</label>
<select id="topic" name="topic">
  <option value="html">HTML</option>
  <option value="css">CSS</option>
</select>

<label for="message">Message</label>
<textarea id="message" name="message"></textarea>

<button type="submit">Send</button>

<select> gives a dropdown of choices, <textarea> is a multi-line text box, and <button type="submit"> triggers the form to send its data.

Built-in Validation

HTML can enforce basic rules without any JavaScript: 

<input type="email" required>
<input type="number" min="1" max="10">
<input type="text" pattern="[A-Za-z]{3,}">
  • required — the field can't be left empty
  • min / max — bounds for numeric input
  • pattern — a regex the value must match; {3,} here means "3 or more characters"

The browser blocks submission and shows a built-in error message if these aren't satisfied — useful for basic checks, though real applications usually validate on the server too, since anything enforced only in the browser can be bypassed.

7. Tables & Media

Tables

Tables are for genuinely tabular data — rows and columns of related values, like a schedule or a price list. They're built from a few tags working together: 

<table>
  <thead>
    <tr>
      <th>Tag</th>
      <th>Purpose</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td><code>table</code></td>
      <td>Wraps the whole table</td>
    </tr>
  </tbody>
</table>
  • <table> — the container for everything
  • <thead> / <tbody> — groups the header row separately from the data rows
  • <tr> — a table row
  • <th> — a header cell (bold, centered by default)
  • <td> — a regular data cell

Worth knowing: tables aren't meant for page layout. That was common practice in the early web, before CSS had better tools for it — today, layout is handled with CSS instead (a topic for another post), and tables are reserved for actual tabular data.

Images

<img src="images/form-example.png" alt="A contact form with email, topic, and message fields" width="400">

src points to the file, and alt is required — it's what a screen reader announces, and what shows if the image fails to load. A useful test: if the image vanished, would the alt text alone still make sense in its place?

Figure and Figcaption

When an image needs a caption, <figure> and <figcaption> pair it semantically, rather than just sitting a stray paragraph near an image: 

<figure>
  <img src="images/form-example.png" alt="A contact form example">
  <figcaption>The form from Section 6, rendered.</figcaption>
</figure>

Video and Audio

<video src="demo.mp4" controls width="500"></video>

<audio src="clip.mp3" controls></audio>

controls adds the browser's built-in play/pause/volume UI. Without it, the media loads but gives the visitor no way to interact with it.

Picture — Responsive Images

<picture> lets the browser choose between different image files depending on screen size, useful for serving a smaller file to phones instead of a full desktop-sized image: 

<picture>
  <source media="(max-width: 600px)" srcset="images/form-small.png">
  <img src="images/form-example.png" alt="A contact form example">
</picture>

The <img> inside is still required as a fallback — it's what displays if none of the <source> conditions match.

8. Accessibility

Section 5 introduced screen readers and why semantic tags matter to them. This section gets more concrete — specific attributes and habits that make a page usable for people who can't rely on sight, a mouse, or fine motor control.

Alt Text

Every meaningful <img> needs an alt attribute — covered briefly in Section 7, worth repeating here as accessibility's most basic rule. A screen reader reads that text aloud in place of the image entirely. 

<img src="chart.png" alt="Bar chart showing sales rising 40% in Q3">

Purely decorative images (a background flourish, a divider graphic) should use an empty alt="" rather than omitting the attribute entirely — this tells the screen reader to skip it silently, instead of reading out the filename as a fallback.

ARIA Labels

Sometimes an element's purpose is visually obvious but has no text a screen reader can read — an icon-only button, for example. aria-label fills that gap: 

<button aria-label="Close menu">
  <svg>...</svg>
</button>

Without it, a screen reader user hears just "button," with no idea what it does. ARIA attributes are a large topic on their own — the rule worth remembering for now is to reach for real semantic HTML first (a real <button>, a real <nav>), and use ARIA to fill in gaps HTML can't express on its own, not as a replacement for it.

Labels and Form Fields

Covered in Section 6, worth restating here as an accessibility rule specifically: every input needs a <label>, connected with for matching the input's id. 

<label for="email">Email</label>
<input type="email" id="email">

A placeholder is not a substitute for a label — placeholder text disappears the moment someone starts typing, and some screen readers don't announce it at all.

Keyboard Navigation

Not everyone uses a mouse or a touchscreen — some visitors navigate a page entirely with a keyboard, tabbing from element to element. A few habits keep that working:

  • Use real <button> and <a> tags for clickable things, not a <div> with a click handler — real elements are keyboard-focusable automatically, a styled <div> isn't
  • Never remove focus outlines with outline: none unless you replace them with an equally visible alternative — that outline is how keyboard users see where they are on the page
  • Keep a logical tab order by following natural document order, rather than jumping around with a manually set tabindex

A quick way to test any page you build: unplug the mouse, and try to use the whole thing with Tab, Shift+Tab, and Enter alone.

9. Going Further

Global Attributes & data-*

Most attributes only work on certain tags: href belongs to links, src to images. Global attributes are the exception. They can go on any element.

  • id — a unique name for one element (what the table of contents links to)
  • class — a reusable label that many elements can share, mainly for CSS and JavaScript to target
  • style — inline CSS for that single element
  • title — extra text shown as a tooltip on hover
  • lang — the language of the content, which helps screen readers pronounce it correctly
  • hidden — hides the element from the page
  • tabindex — controls whether an element can receive keyboard focus

Custom data attributes

Any attribute that starts with data- is yours to invent. The browser ignores it, but JavaScript can read it, which makes it a tidy way to attach extra information to an element: 

<button data-level="beginner" data-topic="forms">Start</button>
const btn = document.querySelector("button");
console.log(btn.dataset.level); // "beginner"

The part after data- becomes a property on dataset. This is the DOM from Section 2 at work: the attribute lives in the tree, and JavaScript can reach it.
